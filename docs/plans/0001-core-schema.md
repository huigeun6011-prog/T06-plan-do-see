# 0001 — Core schema and build order

- **Status:** approved by the human, 2026-11-26; chunks 1-2 built and merged (`9036d53`), the DDL below ran unchanged on `dev` and `test`
- **Author:** Planner (Claude), amended by the Orchestrator after the human's answers
- **Related:** ADR 0003 (stack), ADR 0004 (data model), ADR 0005 (AI recap), `docs/TASK.md` (pass criteria T06-Cxx)

Doping tables, net meso, coin forecast, the "today" suggestion and automatic clear-time measurement are out of scope here.

## 1. Decisions that shape the schema

- **Plans** come in three kinds: `weekly` (Thursday 00:00 KST to next Thursday 00:00), `monthly` (1st 00:00 to next 1st 00:00) and `event` (name, start and end chosen by the human; events may overlap). Achievement is tracked per plan; weekly and monthly are never mixed. The week screen shows this week's and this month's todos together, done ones included, default filter "all".
- **Registrations** (table `entry`) are recurring tasks: weekly or monthly. A new period creates todos from them. Not repeating = a todo inside an event plan, created by hand (`entry_id` NULL). Removing a registration stops future todos; past ones stay.
- **Deadlines** are instants stored at clean times, exclusive end. Late = not done and `due_at <= now`. Display: a stored 00:00 is shown as the previous day 24:00 (Thursday 00:00 shows as "Wed 24:00"); input accepts "end of day (24:00)" and stores the next day 00:00. Other times are shown as they are (e.g. 02:00). For whole-day deadlines this equals the task's date rule (T06-C30).
- **Cumulative todos** have `target_count` (default 1). Each day's progress is one run record with `units` set absolutely, not added, so a double click cannot count twice. Done when the sum of units reaches the target.
- **Miss reason** is a free text of at most 200 characters on the todo. Blocked count = todos with a reason (T06-C31).
- **Improvement**: see ADR 0005 (AI recap on a button) and section 6 (manual path, always available).

## 2. DDL (`db/schema.sql`, idempotent like `db/ping.sql`)

The character table is `game_character` because `character` is an SQL keyword. No `$$` bodies, so an apply script can split the file on `;`.

```sql
CREATE TABLE IF NOT EXISTS game_character (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL CHECK (name <> '') UNIQUE,   -- job name only, never a nickname
  sort_order int  NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- Recurring registrations. Versioned: root_id = id of the first version.
CREATE TABLE IF NOT EXISTS entry (
  id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  root_id       bigint NOT NULL REFERENCES entry(id),
  character_id  bigint REFERENCES game_character(id),     -- NULL = account-level
  title         text   NOT NULL CHECK (title <> ''),
  period_kind   text   NOT NULL CHECK (period_kind IN ('weekly','monthly')),
  clear_minutes int    NOT NULL CHECK (clear_minutes >= 1), -- minutes per unit
  reward_meso   bigint NOT NULL DEFAULT 0 CHECK (reward_meso >= 0),
  party_size    int    NOT NULL DEFAULT 1 CHECK (party_size >= 1),
  doping        text   NOT NULL DEFAULT 'base',
  memo          text   NOT NULL DEFAULT '',
  target_count  int    NOT NULL DEFAULT 1 CHECK (target_count >= 1),
  tags          text[] NOT NULL DEFAULT '{}',
  sort_order    int    NOT NULL DEFAULT 0,
  use_yn        char(1) NOT NULL DEFAULT 'Y' CHECK (use_yn IN ('Y','N')),
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS entry_one_current  ON entry (root_id) WHERE use_yn = 'Y';
CREATE UNIQUE INDEX IF NOT EXISTS entry_one_per_title ON entry (COALESCE(character_id, 0), title) WHERE use_yn = 'Y';

-- Plans: weekly, monthly or event. Versioned the same way.
CREATE TABLE IF NOT EXISTS plan (
  id               bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  root_id          bigint NOT NULL REFERENCES plan(id),
  period_kind      text NOT NULL CHECK (period_kind IN ('weekly','monthly','event')),
  title            text NOT NULL DEFAULT '',
  starts_at        timestamptz NOT NULL,                 -- clean KST boundary
  ends_at          timestamptz NOT NULL,                 -- exclusive
  priority         smallint NOT NULL DEFAULT 2 CHECK (priority BETWEEN 1 AND 3), -- 1 = highest
  success_criteria text NOT NULL CHECK (success_criteria <> ''),
  expected_minutes int  NOT NULL DEFAULT 0 CHECK (expected_minutes >= 0),
  use_yn           char(1) NOT NULL DEFAULT 'Y' CHECK (use_yn IN ('Y','N')),
  created_at       timestamptz NOT NULL DEFAULT now(),
  CHECK (ends_at > starts_at)
);
CREATE UNIQUE INDEX IF NOT EXISTS plan_one_current ON plan (root_id) WHERE use_yn = 'Y';
CREATE UNIQUE INDEX IF NOT EXISTS plan_one_per_period ON plan (period_kind, starts_at)
  WHERE use_yn = 'Y' AND period_kind <> 'event';

-- Todos: edited in place; delete = use_yn 'N'. plan_id / entry_id always hold the ROOT id.
CREATE TABLE IF NOT EXISTS todo (
  id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  plan_id          bigint NOT NULL REFERENCES plan(id),
  entry_id         bigint REFERENCES entry(id),          -- NULL for hand-made todos
  source_plan_id   bigint REFERENCES plan(id),           -- set when this todo is a retro improvement
  title            text NOT NULL CHECK (title <> ''),
  note             text NOT NULL DEFAULT '',
  character_id     bigint REFERENCES game_character(id),
  due_at           timestamptz NOT NULL,                 -- clean boundary; generated = plan.ends_at
  priority         smallint NOT NULL DEFAULT 2 CHECK (priority BETWEEN 1 AND 3),
  tags             text[] NOT NULL DEFAULT '{}',
  expected_minutes int NOT NULL DEFAULT 0 CHECK (expected_minutes >= 0), -- per unit x target
  target_count     int NOT NULL DEFAULT 1 CHECK (target_count >= 1),
  miss_reason      text CHECK (miss_reason IS NULL OR (miss_reason <> '' AND char_length(miss_reason) <= 200)),
  use_yn           char(1) NOT NULL DEFAULT 'Y' CHECK (use_yn IN ('Y','N')),
  created_at       timestamptz NOT NULL DEFAULT now(),
  UNIQUE (plan_id, entry_id)                              -- idempotent generation; NULL entry_id exempt
);
CREATE UNIQUE INDEX IF NOT EXISTS todo_one_improvement ON todo (source_plan_id)
  WHERE source_plan_id IS NOT NULL AND use_yn = 'Y';
CREATE INDEX IF NOT EXISTS todo_plan_idx ON todo (plan_id);

-- Run records: one row per todo per Seoul day. Edited in place; delete = use_yn 'N'.
CREATE TABLE IF NOT EXISTS run_record (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  todo_id        bigint NOT NULL REFERENCES todo(id),
  run_date       date   NOT NULL,                        -- Seoul date, supplied by the app
  units          int    NOT NULL DEFAULT 1 CHECK (units >= 1),  -- that day's count, set not added
  started_at     timestamptz,
  ended_at       timestamptz,
  actual_minutes int CHECK (actual_minutes >= 0),        -- NULL = not entered
  done           boolean NOT NULL DEFAULT true,          -- false = un-completed, row and minutes kept
  use_yn         char(1) NOT NULL DEFAULT 'Y' CHECK (use_yn IN ('Y','N')),
  created_at     timestamptz NOT NULL DEFAULT now(),
  CHECK (started_at IS NULL OR ended_at IS NULL OR ended_at >= started_at)
);
CREATE UNIQUE INDEX IF NOT EXISTS run_one_per_day ON run_record (todo_id, run_date) WHERE use_yn = 'Y';

-- Single definition of "done / actual / blocked" for every read.
CREATE OR REPLACE VIEW todo_state AS
SELECT t.*,
       COALESCE(r.done_n, 0)      AS done_n,
       COALESCE(r.actual, 0)      AS actual_minutes,
       (t.miss_reason IS NOT NULL) AS blocked,
       COALESCE(r.done_n, 0) >= t.target_count AS is_done
FROM todo t
LEFT JOIN (
  SELECT todo_id,
         COALESCE(sum(units) FILTER (WHERE done), 0)::int AS done_n,
         COALESCE(sum(actual_minutes), 0)::int AS actual
  FROM run_record WHERE use_yn = 'Y' GROUP BY todo_id
) r ON r.todo_id = t.id
WHERE t.use_yn = 'Y';
```

Driver conventions (matter for T06-C35): select timestamps and dates as text or ISO strings, cast `count`/`sum` to `::int`, bigint ids come back as strings, pass tags as a JS array. Chunk 1 must test array and date handling against Neon. The DDL has never been run; the `root_id` self-reference insert and `ON CONFLICT ... WHERE use_yn='Y'` are the riskiest parts, test them first.

## 3. Versioning (plan and entry only)

First row: `root_id = id`. Every edit adds a row with the same `root_id` and flips the old row to `use_yn='N'`. Todos and run records point at the root id. A root row is never deleted. Create in one statement with `WITH n AS (SELECT nextval(pg_get_serial_sequence('plan','id')) AS id) INSERT ... SELECT n.id, n.id, ...`. Edit with `sql.transaction([...])`: (1) `UPDATE ... SET use_yn='N' WHERE root_id=$ AND use_yn='Y'`, (2) `INSERT ... WHERE NOT EXISTS (current row)`. If the insert affects 0 rows, show "someone edited first, reload". Do not merge into one CTE (the ordering of UPDATE and INSERT inside one statement is not defined and the unique index can fire). Original = `WHERE root_id=$ ORDER BY id`, first row (T06-C08). Entry edits change future todos only; todos hold a snapshot.

## 4. Periods and generation

- One clock: a TypeScript helper `todaySeoul(now)` using `Intl` with `Asia/Seoul`; `now` is a parameter so tests can inject it. The server runs in UTC; never use the server's local date and no SQL `CURRENT_DATE`.
- `periodFor(kind, instant)`: weekly = most recent Thursday 00:00 KST to the next one; monthly = 1st 00:00 to the next 1st 00:00. KST has no DST.
- On every access of the current weekly or monthly period (and the next one only): insert the plan with `ON CONFLICT (period_kind, starts_at) WHERE use_yn='Y' AND period_kind <> 'event' DO NOTHING`, then generate todos from active registrations of that kind with `ON CONFLICT (plan_id, entry_id) DO NOTHING` (`due_at = plan.ends_at`, `expected_minutes = clear_minutes * target_count`). Idempotent, safe in parallel, heals after a crash, no cron. A soft-deleted generated todo never returns. A registration added mid-period appears on the next access.
- Event plans are created by hand and never generated. Hand-made todos may be added to any plan.

## 5. Todo and run rules

- Complete (set that day's units): `INSERT INTO run_record (...) VALUES (...) ON CONFLICT (todo_id, run_date) WHERE use_yn='Y' DO UPDATE SET done = true, units = EXCLUDED.units`. Minutes are kept when the new value is empty. A second click or a parallel request changes nothing (T06-C21, C22).
- Un-complete: `done = false`; row and minutes stay; completing again the same day restores them.
- Quick tick with no minutes: `actual_minutes` stays NULL; the retro shows how many done runs have no minutes.
- Search, filter, sort (T06-C18 to C20) run in SQL through `sql.query(text, params)` with a whitelist of ORDER BY fragments; values only as `$n`; search with `strpos(lower(...), lower($q)) > 0`; tie-breaker `id ASC`; the screen prints the sort rule.

## 6. Retro (computed on read)

```sql
SELECT count(*)::int AS plan_count,
       count(*) FILTER (WHERE is_done)::int AS done_count,
       count(*) FILTER (WHERE NOT is_done AND due_at <= $2::timestamptz)::int AS late_count,
       count(*) FILTER (WHERE blocked)::int AS blocked_count,
       COALESCE(sum(expected_minutes),0)::int AS expected_minutes,
       COALESCE(sum(actual_minutes),0)::int AS actual_minutes,
       (COALESCE(sum(actual_minutes),0) - COALESCE(sum(expected_minutes),0))::int AS diff_minutes
FROM todo_state WHERE plan_id = $1;
```

`$2` is the current instant supplied by the app. Empty data gives 0. A done todo is never late. Every number links to `/plan/<id>?scope=all|done|late|blocked` and the list uses the same predicates; a test asserts each aggregate equals its list length (T06-C83). The plan's own `expected_minutes` (T06-C07) and the retro's expected sum (T06-C32) are different numbers; label them separately. Also: a history table with one row per plan, and the same aggregate grouped by character or tag.

Improvement (T06-C33): the human may type one line, or use the AI recap (ADR 0005). Either way it is saved as a todo in the next plan with `source_plan_id` set and tag `improvement`, unique per plan. Next plan: weekly retro gives next week, monthly gives next month, event gives the current week. Nothing is ever forced and no prompt blocks reading; the home page may show a dismissible note listing ended plans without a retro.

## 7. Export and contract

`GET /export` returns one JSON file from one SELECT (consistent snapshot), including soft-deleted and old-version rows, dates ISO, timezone stated. `contracts/pds-schema-v2.json` lists version, timezone, date rules, units, enums, tables with columns, keys, uniques and relations, and aggregate definitions; a Vitest test compares its table and column names to `information_schema` on the test database.

## 9. Risks

- `plan_id` and `entry_id` must hold the root id; a foreign key cannot enforce it, so one test covers it.
- The DDL is untested; chunk 1 is the first real check.
- Public, login-free: the export contains everything including soft-deleted rows; only job names and short texts may be entered. Login arrives in task 7.
- Dev and test use Neon branches `dev` and `test`; `production` holds the real data and must not be touched by development or tests.
